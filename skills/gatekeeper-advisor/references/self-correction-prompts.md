# Self-Correction 프롬프트 레퍼런스

Gatekeeper의 Self-Correction 경로에서 사용하는 자가 진단 프롬프트 변형, 도메인별 예시, Advisor 에이전트 정의 템플릿을 제공한다.

---

## 목차

1. 자가 진단 프롬프트 — 도메인별 변형
2. 판단 시나리오 예시
3. Advisor 호출 컨텍스트 예시
4. Advisor 에이전트 정의 템플릿
5. 자가 진단 실패 패턴 (안티패턴)

## 1. 자가 진단 프롬프트 — 도메인별 변형

기본 프롬프트 템플릿을 도메인에 맞게 변형한다. 핵심 구조([P][C][D][B][R] 5개 축)는 동일하게 유지한다.

### 1-1. 코드 구현 작업

```
## 자가 진단 — 코드 구현

작업: {기능 이름 또는 이슈 제목}
시도: {N}번

[P] 진행률: 구현 완료 비율? (0 / 25 / 50 / 75 / 100)
    - 0: 시작 못함
    - 25: 구조만 잡힘
    - 50: 핵심 로직 작성 중
    - 75: 구현 완료, 테스트 실패 중
    - 100: 테스트 통과

[C] 신뢰도: 현재 방향이 맞다는 확신? (낮음 / 중간 / 높음)
    - 낮음: 어떤 에러인지도 모름, 또는 접근법 자체가 잘못됐을 것 같음
    - 중간: 방향은 맞지만 세부 구현이 불확실
    - 높음: 에러 원인을 알고 있고 수정 방법도 확실함

[D] 다양성: 최근 3번의 시도가 서로 다른 접근법이었나? (예 / 아니오)
    - 예: 다른 라이브러리, 다른 알고리즘, 다른 파일 구조 시도
    - 아니오: 같은 코드를 조금씩 수정하는 반복

[B] 장애물: 현재 해결 안 된 에러나 제약이 있나? (있음 / 없음)
    - 있음이라면: 에러 메시지 또는 제약 설명 포함

[R] 자원: 이미 쓴 시도 횟수 대비 진전이 납득할 만한가? (예 / 아니오)
    - 아니오: 5번 이상 시도했는데 [P]가 50 이하
```

### 1-2. 리서치/조사 작업

```
## 자가 진단 — 리서치

주제: {조사 주제}
시도: {N}번

[P] 진행률: 필요한 정보 수집 완료 비율? (0 / 25 / 50 / 75 / 100)
[C] 신뢰도: 지금까지 찾은 정보가 신뢰할 수 있나? (낮음 / 중간 / 높음)
    - 낮음: 출처가 불분명하거나 상충하는 정보가 많음
    - 중간: 일부 확인됐지만 핵심 부분이 빠짐
    - 높음: 신뢰할 수 있는 출처로 충분히 확인됨
[D] 다양성: 다른 검색어/출처/관점을 충분히 탐색했나? (예 / 아니오)
[B] 장애물: 접근 불가능한 정보나 막힌 검색 경로가 있나? (있음 / 없음)
[R] 자원: 검색 횟수 대비 유의미한 정보를 찾고 있나? (예 / 아니오)
```

### 1-3. 분석/설계 작업

```
## 자가 진단 — 분석/설계

목표: {설계하려는 것}
시도: {N}번

[P] 진행률: 설계 완성도? (0 / 25 / 50 / 75 / 100)
[C] 신뢰도: 현재 설계가 요구사항을 충족할 확신? (낮음 / 중간 / 높음)
    - 낮음: 핵심 트레이드오프를 아직 파악 못함
    - 중간: 방향은 잡혔지만 엣지 케이스가 불안
    - 높음: 주요 결정이 근거와 함께 확립됨
[D] 다양성: 여러 대안 설계를 충분히 검토했나? (예 / 아니오)
[B] 장애물: 결정을 내리지 못하게 막는 불확실성이 있나? (있음 / 없음)
[R] 자원: 이미 검토한 범위 대비 설계가 구체화됐나? (예 / 아니오)
```

## 2. 판단 시나리오 예시

### 시나리오 A: Advisor 호출 필수 (코드 구현)

```
[P] 25
[C] 낮음  ← "fetchJson 에러가 왜 나는지 모르겠음"
[D] 아니오  ← "같은 코드를 3번 조금씩 수정만 함"
[B] 있음  ← "TypeError: Cannot read properties of undefined"
[R] 아니오  ← "4번 시도했는데 아직 기본 연결도 안 됨"
```

결정: **[C]=낮음 + [D]=아니오** → Advisor 호출 필수

Advisor에게 전달할 것: 에러 메시지 전문, 현재 코드 스니펫, 시도한 수정 목록

### 시나리오 B: 계속 진행 (리서치)

```
[P] 75
[C] 높음  ← "3개 공식 출처에서 확인됨"
[D] 예  ← "공식 문서, 논문, 커뮤니티 토론 모두 확인"
[B] 없음
[R] 예  ← "5번 검색으로 핵심 정보 확보"
```

결정: **[C]=높음** → Advisor 불필요, 계속 진행

### 시나리오 C: Advisor 호출 권장 (설계)

```
[P] 50
[C] 중간  ← "방향은 맞는 것 같은데 확신이 없음"
[D] 예  ← "Event-driven vs polling 두 가지 검토함"
[B] 있음  ← "실시간 요구사항이 명확하지 않아 결정 못함"
[R] 예
```

결정: **[B]=있음 + [C]=중간(낮음에 가까움)** → Advisor 호출 권장

Advisor에게: 불명확한 요구사항에 대한 결정 기준 요청

### 시나리오 D: Advisor 호출 필수 ([D]=아니오 3회 연속)

이터레이션 기록:
- 이터레이션 1: [D]=아니오 (같은 import 경로 수정 반복)
- 이터레이션 2: [D]=아니오 (여전히 같은 접근)
- 이터레이션 3: [D]=아니오 (또 같은 수정)

결정: **[D]=아니오 3회 연속** → Advisor 호출 필수

이 패턴은 에이전트가 창의적 대안을 생각하지 못하고 로컬 최솟값에 갇혔음을 의미한다.

## 3. ACP 작성 예시 (압축 전/후 비교)

Advisor에게 전달하는 컨텍스트는 ACP(Advisor Context Package) 포맷으로 압축한다.
압축하지 않으면 Advisor가 노이즈 필터링에 추론을 낭비하고 진단 품질이 저하된다.

### 예시 A: 코드 구현 교착 (환경 변수 문제)

**압축 전 — 전체 히스토리 전달 (❌ 비효율, ~420 토큰):**

```
Advisor, 도와줘. Next.js와 Supabase를 연결하려고 하는데 계속 문제가 생겨.

배경: 우리 프로젝트는 Next.js 14 App Router를 쓰고 있고, Supabase를 백엔드로 사용해.
처음에 createClient()를 직접 api/route.ts에서 호출했는데 "supabaseUrl is required"라는
에러가 났어. 그래서 공식 문서를 보니까 서버 사이드에서는 createServerClient()를 써야 한다고
해서 변경했는데 여전히 같은 에러야. 혹시 환경 변수 이름 문제인가 해서
NEXT_PUBLIC_SUPABASE_URL로 바꿨는데 그래도 안 돼. .env.local 파일을 열어서 직접 확인해보니
값은 분명히 있는데 process.env로 읽으면 undefined가 나와. 정말 모르겠어.

내가 시도한 것들:
- createClient() → supabaseUrl is required 에러
- createServerClient()로 변경 → 동일 에러  
- NEXT_PUBLIC_ 접두사 추가 → 동일 에러
- .env.local 값 재확인 → 값은 있는데 읽기가 안 됨

Supabase + Next.js 13 App Router에서 서버 사이드 환경 변수를 어떻게 써야 해?
```

**압축 후 — ACP 포맷 (✅ 효율, ~180 토큰):**

```
## ACP

[TRIGGER] C=낮음 + D=아니오 (4회 동일 에러)
[GOAL]    Next.js 14 App Router route.ts에서 Supabase 클라이언트 초기화
[HARD_CONSTRAINTS] Next.js 14, App Router, Supabase JS v2, .env.local 사용
[ATTEMPTS]
  A1: [라이브러리 호출] createClient() → "supabaseUrl is required"
  A2: [API 변경] createServerClient() → 동일 에러
  A3: [환경변수명] NEXT_PUBLIC_ 접두사 추가 → 동일 에러
  A4: [파일 확인] .env.local 값 재확인 → process.env 출력 시 undefined
[BLOCKER]
  type: ConfigurationError
  loc:  app/api/route.ts:3
  msg:  "supabaseUrl is required" (createClient 초기화 시점)
[HYPOTHESIS]
  H1 (60%): Next.js 서버 컴포넌트에서 NEXT_PUBLIC_ 없는 변수는 런타임에만 주입됨
  H2 (30%): .env.local이 올바른 위치(프로젝트 루트)에 없음
[ASK] App Router route.ts에서 서버 전용 환경 변수를 Supabase에 전달하는 올바른 방법은?
```

절감 효과: ~420 → ~180 토큰 (57% 감소). Advisor는 진단에만 집중할 수 있다.

### 예시 B: 리서치 교착 (검색 전략 막힘)

**압축 전 (❌ ~280 토큰):**

```
Redis Cluster와 Redis Sentinel 비교 자료를 찾고 있는데 도움이 필요해.
"Redis Cluster vs Sentinel"로 검색했는데 공식 문서만 나오고,
"Redis high availability comparison"으로도 검색했는데 비슷한 결과야.
"Redis Cluster production"으로도 해봤는데 마케팅 문서들만 나와.
실제 운영 관점의 트레이드오프 자료를 못 찾겠어. 어떻게 검색하면 될까?
```

**압축 후 — ACP (✅ ~120 토큰):**

```
## ACP

[TRIGGER] D×3회 (동일 유형 검색 반복)
[GOAL]    Redis Cluster vs Sentinel 운영 트레이드오프 파악 (장애복구 시간, 운영 복잡성)
[HARD_CONSTRAINTS] 없음
[ATTEMPTS]
  ×3: [키워드 검색] "Redis Cluster/HA/production" 변형 → 공식문서/마케팅만
[BLOCKER]
  type: 정보 접근 불가
  loc:  없음 (출력 부재)
  msg:  실제 운영 경험 기반 비교 자료 없음
[HYPOTHESIS]
  H1 (80%): 공식문서 중심 검색어 → 기술 블로그/포스트모텀 검색어로 전환 필요
[ASK] "운영 경험 기반" 비교 자료를 찾는 검색 전략 3가지 제시해줘
```

### ACP 작성 시 제외할 것

다음은 Advisor에게 전달해도 진단에 도움이 되지 않는 내용이다. 모두 제외한다:

| 제외 대상 | 이유 | 대체 표현 |
|----------|------|----------|
| 전체 파일 내용 | Advisor가 직접 읽을 수 있음 | `loc: app/api/route.ts:3` (경로만) |
| 전체 스택 트레이스 | 첫 줄만 의미 있음 | `msg:` 에 첫 줄만 |
| 시도의 이유와 추론 과정 | 결과만 필요 | `→ {결과 5단어}` |
| 배경 설명 | Advisor는 도메인 지식 보유 | 생략 |
| 동일 에러 N회 반복 | 패턴만 전달 | `×N: [반복]` |
| 성공한 초기 단계 | 현재 막힌 지점만 중요 | 생략 |

```markdown
---
name: advisor
description: "막힌 작업 에이전트에게 새로운 관점과 접근법을 제시하는 Advisor. Gatekeeper가 교착 상태를 감지했을 때 호출됨."

# Advisor — 교착 해소 전문가

Gatekeeper 판단 로직에 의해 호출된다. 작업 에이전트가 스스로 해결하지 못한 문제에 새로운 관점과 구체적인 다음 단계를 제시한다.

## 핵심 역할

1. 호출 컨텍스트를 분석하여 교착의 근본 원인 진단
2. 기존 접근법의 맹점 파악 (에이전트가 보지 못한 것)
3. 구체적이고 실행 가능한 대안 접근법 제시
4. 우선순위가 명확한 다음 단계 지시

## 작업 원칙

- **진단 먼저, 처방 나중**: 호출 컨텍스트를 충분히 읽기 전에 해결책을 제시하지 않는다
- **근본 원인에 집중**: 표면적 증상이 아닌 교착의 근본 원인을 찾는다
- **실행 가능성 우선**: 이론적으로 옳은 답보다 지금 당장 시도할 수 있는 답을 우선한다
- **단계 명확화**: "이렇게 해봐"가 아니라 "1. A를 먼저 확인하고, 2. B를 시도하고, 3. 여전히 실패하면 C를 해"

## 응답 포맷

```
## Advisor 진단 결과

**근본 원인:**
{교착의 실제 원인 — 에이전트가 놓친 것}

**기존 접근법의 문제:**
{왜 지금까지의 시도가 효과 없었는지}

**권장 접근법:**
1. {첫 번째 시도할 것 — 가장 가능성 높은 것}
2. {첫 번째 실패 시 두 번째 대안}
3. {두 번째도 실패 시 세 번째 대안}

**주의사항:**
{이 접근법을 시도할 때 빠지기 쉬운 함정}

**성공 기준:**
{이 단계가 완료됐는지 어떻게 확인하는지}
```

## 에러 핸들링

- 컨텍스트 정보가 부족하면: 작업 에이전트에게 SendMessage로 추가 정보 요청
- 해결책이 불확실하면: 가장 확신도가 높은 가설을 명시하고 제시
- 해결 불가능한 근본 문제이면: 사용자 에스컬레이션 요청

## 협업

- 호출자: Gatekeeper가 감지한 작업 에이전트
- 출력 대상: 호출한 작업 에이전트 (SendMessage 또는 반환값)
- 오케스트레이터: Advisor 호출 결과를 오케스트레이터에게도 요약 전달
```

## 5. 자가 진단 실패 패턴 (안티패턴)

### 안티패턴 1: 낙관 편향

```
❌ 잘못된 자가 진단:
[C] 높음  ← "방법이 있을 것 같음" (근거 없는 낙관)
[D] 아니오 ← 인식하지만 무시
→ Advisor 호출 안 함 → 루프 지속
```

**해결:** [D]=아니오일 때는 [C]에 관계없이 "연속 카운터"를 올린다.

### 안티패턴 2: 진단의 자기기만

```
❌ 잘못된 자가 진단:
[D] 예  ← "이번엔 다른 방법 씀" (실제로는 같은 접근의 사소한 변형)
```

**해결:** "의미 있게 달랐나"의 기준을 명시한다:
- 의미 있는 다름: 다른 라이브러리, 다른 알고리즘, 다른 아키텍처
- 의미 없는 다름: 변수명 변경, 순서 변경, 미세 파라미터 조정

### 안티패턴 3: Advisor 호출 회피

```
❌ 패턴: [C]=낮음임을 알면서 "한 번만 더 시도해보자"
```

이 패턴이 발생하는 이유: 에이전트가 Advisor 호출을 "실패 인정"으로 인식하기 때문.

**리프레이밍:** Advisor 호출은 실패가 아니라 **전략 업그레이드**다. 막힌 상태에서 자원을 낭비하는 것이 실제 실패다. 결정 규칙 테이블은 규칙이 아니라 최적 자원 배분 기준이다.

### 안티패턴 4: 과도한 Advisor 호출

```
❌ 패턴: 조금만 불확실해도 즉시 Advisor 호출
→ Advisor 호출 비용 폭증
```

**해결:** [C]=중간이고 [D]=예이면 계속 진행한다. Advisor는 [B]=있음 or [C]=낮음 or [D]=아니오 연속일 때만 호출한다.
