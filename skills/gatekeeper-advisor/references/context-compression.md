# ACP 컨텍스트 압축 — 알고리즘 및 토큰 버짓 규칙

Advisor(Opus) 호출 시 전달하는 ACP(Advisor Context Package) 구성 규칙. 전체 히스토리를 그대로 전달하면 Advisor의 추론이 노이즈 필터링에 분산된다. ACP는 진단에 필요한 최소 정보만 정제된 포맷으로 전달한다.

## 1. ACP 토큰 버짓

| 섹션 | 목표 | 상한 | 초과 시 조치 |
|------|------|------|------------|
| `[TRIGGER]` | 10 | 20 | 결정 규칙 코드만 (설명 없이) |
| `[GOAL]` | 40 | 80 | 목적어+동사 구조로 단축 |
| `[HARD_CONSTRAINTS]` | 40 | 80 | key:value 쌍으로만 |
| `[ATTEMPTS]` | 120 | 250 | 반복 패턴 콜랩스 적용 |
| `[BLOCKER]` | 60 | 100 | 에러 핑거프린트 규칙 적용 |
| `[HYPOTHESIS]` | 60 | 100 | 최대 2개, 신뢰도 포함 |
| `[ASK]` | 30 | 50 | 단일 질문으로 제한 |
| **ACP 전체** | **360** | **680** | 상한 초과 시 ATTEMPTS 우선 축소 |

**왜 이 버짓인가:** Opus의 실질적인 진단 품질은 컨텍스트 크기보다 정보 밀도에 달려 있다. 500 토큰의 고밀도 ACP가 3000 토큰의 원시 히스토리보다 진단 정확도가 높다. Advisor가 읽어야 할 내용이 적을수록 추론이 핵심 문제에 집중된다.

## 2. 섹션별 압축 규칙

### 2-1. [TRIGGER] — 결정 규칙 코드

자가 진단 결과나 Outer Loop 감지 결과를 1줄 코드로 표현한다.

```
Self-Correction 트리거:
  C=낮음+D=아니오           # 신뢰도 낮음 + 다양성 없음
  D×3                       # [D]=아니오 3회 연속
  P≤25+R=아니오             # 진행률 25% 이하 + 자원 효율 부족
  B=있음+C=낮음             # 장애물 있음 + 신뢰도 낮음

Outer Loop 트리거:
  OL:stagnation×2           # 외부 루프 감지, 2회 무변화
  OL:stagnation×2+file_노_change  # 파일 변화도 없음
  OL:task_frozen:researcher-1     # 특정 팀원 태스크 교착
```

### 2-2. [GOAL] — 목표 압축

**포함:** 달성하려는 관찰 가능한 결과 (완료 조건이 명확한 것)
**제외:** 배경, 동기, 이미 완료된 선행 작업

```
❌ 압축 전:
"우리 팀은 최근 Next.js로 마이그레이션 중이고, Supabase를 도입해서
사용자 인증과 데이터 조회를 구현하려고 해. 이번 태스크는 그 첫 번째
단계인 클라이언트 초기화 문제야."

✅ 압축 후:
"Next.js 14 App Router route.ts에서 Supabase 클라이언트 초기화"
```

### 2-3. [HARD_CONSTRAINTS] — 제약 추출

**포함 기준:** 이 제약을 변경하면 작업 정의 자체가 바뀌는 것
**제외 기준:** 선호도, 권장 사항, 이미 충족된 제약

```
포함 예시:
  runtime: Node 18 (변경 불가)
  db: Postgres 14 (운영 환경 고정)
  api: 외부 결제 API v2 (계약으로 고정)
  auth: SSO 필수 (보안 요구사항)

제외 예시:
  "TypeScript 권장" (변경 가능한 선호도)
  "테스트 커버리지 80%" (선택적 목표)
  "React 18 사용 중" (이미 알려진 사실)
```

제약이 없으면: `[HARD_CONSTRAINTS] 없음`

### 2-4. [ATTEMPTS] — 시도 로그 압축

각 시도를 1줄로 압축한다. 형식: `A{N}: [{유형}] {내용 한 줄} → {결과 5단어}`

**접근법 유형 태그:**
- `[라이브러리]`: 다른 라이브러리/패키지 사용
- `[API변경]`: 같은 기능의 다른 API 호출
- `[설정]`: 설정 파일/환경 변수 조정
- `[로직]`: 알고리즘/로직 변경
- `[구조]`: 파일/폴더 구조 변경
- `[검색]`: 검색어/출처 변경 (리서치 작업)
- `[확인]`: 기존 내용 재확인 (새 시도 아님)

**콜랩스 규칙 (반복 패턴 압축):**

```
동일 결과가 2회 이상 연속이면 콜랩스:

개별 표기 (압축 전):
  A2: [설정] NEXT_PUBLIC_ 접두사 추가 → supabaseUrl required 에러
  A3: [설정] SUPABASE_URL 이름 변경 → supabaseUrl required 에러
  A4: [확인] .env.local 파일 내용 확인 → supabaseUrl required 에러

콜랩스 (압축 후):
  ×3: [설정/확인] 환경변수명 변형 및 파일 확인 → supabaseUrl required 반복
```

**신규 정보 없는 시도는 콜랩스 대상:**
"같은 에러가 3번 나왔다"는 사실만으로 충분하고, 세 번의 개별 설명은 필요 없다.

### 2-5. [BLOCKER] — 에러 핑거프린트

전체 스택 트레이스 대신 3개 필드로 압축한다:

```
type: {에러 분류}
  - TypeError / ReferenceError / NetworkError
  - ConfigurationError / AuthError / PermissionError
  - LogicError (예외 없이 잘못된 결과 반환)
  - 출력 부재 (에러 없이 결과가 없는 경우)

loc: {파일:라인 번호}
  - 특정 위치가 있으면: "app/api/route.ts:12"
  - 런타임 발생이면: "런타임 (빌드는 통과)"
  - 위치 불명이면: "미확인"

msg: {에러 메시지 첫 의미있는 줄, 100자 이내}
  - "supabaseUrl is required" (전체 메시지가 짧으면 전체)
  - "TypeError: Cannot read properties of undefined (reading 'map')" (긴 것은 첫 줄)
  - 에러 없이 빈 결과면: "응답 없음 (status: 200, body: {})"
```

### 2-6. [HYPOTHESIS] — 가설 압축

최대 2개, 신뢰도(%) 포함. 이미 시도했다 실패한 가설은 제외한다.

```
✅ 올바른 가설:
  H1 (70%): App Router route.ts는 NEXT_PUBLIC_ 없는 변수를 빌드 시 번들 안 함
  H2 (25%): .env.local이 monorepo 루트가 아닌 패키지 내부에 위치

❌ 잘못된 가설 (이미 시도해서 기각됨):
  H: NEXT_PUBLIC_ 접두사 누락 → A3에서 이미 시도, 동일 에러

신뢰도 배분 원칙:
  - 모든 가설의 합이 100%일 필요 없음
  - 신뢰도가 20% 미만이면 포함 가치 없음 (제외)
  - 단일 가설이 90%+ 이면 1개만 포함해도 충분
```

### 2-7. [ASK] — 단일 질문화

여러 질문을 하나로 압축한다. 가능하면 선택지 형태로 구성한다.

```
❌ 압축 전 (여러 질문):
"환경 변수 문제인가요? 아니면 createServerClient 사용법이 잘못됐나요?
그리고 NEXT_PUBLIC_ 접두사는 언제 써야 하나요? 또 .env.local 말고
다른 파일을 써야 하나요?"

✅ 압축 후 (단일 질문):
"App Router route.ts에서 서버 전용 환경 변수를 Supabase에 전달하는 올바른 패턴은?"

또는 선택지 형태:
"H1(서버 번들링 문제) vs H2(.env 위치 문제) 중 어느 것이 맞고, 검증 방법은?"
```

## 3. Self-Correction ACP 구성 절차

자가 진단([P][C][D][B][R])이 Advisor 호출 조건을 충족한 후, ACP를 구성하는 단계별 절차:

```
Step 1. TRIGGER 결정
  자가 진단 결과를 결정 규칙 코드로 변환
  예: [C]=낮음 + [D]=아니오 → "C=낮음+D=아니오"

Step 2. GOAL 작성
  현재 태스크 제목에서 동사+목적어만 추출
  배경 제거, 2문장 이내

Step 3. HARD_CONSTRAINTS 추출
  태스크 설명에서 "변경 불가" 표시된 제약만 추출
  없으면 "없음"

Step 4. ATTEMPTS 로그 구성
  최근 N번의 시도를 유형 태그와 함께 1줄씩
  동일 결과가 2회 이상이면 콜랩스
  이미 기각된 가설의 시도는 콜랩스 대상

Step 5. BLOCKER 핑거프린트
  현재 발생하는 에러/막힘의 type, loc, msg 추출
  전체 스택 트레이스는 참조 경로만 남김 (필요하면 Advisor가 요청)

Step 6. HYPOTHESIS 정제
  이미 시도해서 기각된 가설 제거
  남은 가설 중 신뢰도 상위 2개만

Step 7. ASK 단일화
  "이 문제를 해결하기 위해 Advisor가 알려줘야 할 것"을 한 문장으로
```

## 4. Outer Loop ACP 구성 절차

오케스트레이터가 스냅샷 비교로 교착을 감지했을 때, StateSnapshot 히스토리에서 ACP를 구성한다:

```
입력: snapshot_history[N-stagnation_count : N]  # 교착 기간의 스냅샷들
출력: ACP

Step 1. TRIGGER
  "OL:stagnation×{count}" + 교착 유형 추가
  파일 변화 없음: "+file_no_change"
  태스크 전환 없음: "+task_frozen:{agent_name}"

Step 2. GOAL
  오케스트레이터가 해당 에이전트에게 할당한 태스크 제목 + 기대 결과

Step 3. HARD_CONSTRAINTS
  에이전트 정의에서 명시된 제약 (도구 접근 제한 등)

Step 4. ATTEMPTS — 스냅샷 델타로 구성
  각 스냅샷 이터레이션을 1줄로:
  IT{N}: workspace_변화={있음/없음}, task_전환={있음/없음}, 출력요약="{100자}"
  
  콜랩스 적용:
  ×2: workspace_변화=없음, task_전환=없음, 출력요약="[재시도 메시지 반복]"

Step 5. BLOCKER
  type: 교착 유형 (파일 미생성 / 태스크 미전환 / 출력 반복)
  loc:  교착 에이전트 이름 + 태스크 제목
  msg:  교착 에이전트의 마지막 출력 요약 (100자)

Step 6. HYPOTHESIS
  교착 원인 가설:
  - 외부 의존성 미충족 (다른 에이전트 결과 대기 중)
  - 도구 접근 권한 부족
  - 태스크 정의 불명확
  - 기술적 막힘 (에러 반복)

Step 7. ASK
  교착 해소를 위한 구체적 지시 요청
```

**Outer Loop ACP 예시:**

```
## ACP

[TRIGGER] OL:stagnation×2+task_frozen:researcher-1
[GOAL]    Redis Cluster vs Sentinel 운영 트레이드오프 비교 (장애복구시간, 운영복잡성)
[HARD_CONSTRAINTS] WebSearch 사용 가능, 영문/한국어 모두 허용
[ATTEMPTS]
  ×2: workspace_변화=없음, task_전환=없음, 출력=["Redis Cluster vs Sentinel 검색 결과 없음" 반복]
[BLOCKER]
  type: 정보 접근 불가 (출력 부재)
  loc:  researcher-1 / "Redis HA 비교 조사" 태스크
  msg:  "공식 문서 외 운영 경험 기반 자료 없음"
[HYPOTHESIS]
  H1 (75%): 검색어가 공식문서 인덱스에 최적화 → 기술블로그/포스트모텀 키워드 필요
  H2 (20%): 한국어 검색 편향 → 영문 커뮤니티 직접 검색 필요
[ASK] researcher-1이 지금 당장 시도할 수 있는 검색 전략 2가지 알려줘
```

## 5. 압축 품질 체크리스트

ACP를 전달하기 전 다음을 확인한다:

```
[ ] TRIGGER: 결정 규칙 코드가 명확한가? (한 줄 이내)
[ ] GOAL: 배경 설명이 없고 관찰 가능한 결과만 있는가?
[ ] HARD_CONSTRAINTS: 선호도가 아닌 변경 불가 제약만 있는가?
[ ] ATTEMPTS: 
    - 각 시도가 1줄인가?
    - 동일 결과 2회 이상은 콜랩스됐는가?
    - 이미 기각된 가설 기반 시도는 콜랩스됐는가?
    - 성공한 초기 단계는 제외됐는가?
[ ] BLOCKER: 전체 스택 트레이스 대신 3개 필드(type/loc/msg)만 있는가?
[ ] HYPOTHESIS: 이미 시도해 기각된 가설이 포함되지 않았는가?
[ ] ASK: 질문이 하나인가? 선택지 형태로 구성됐는가?
[ ] 전체 ACP가 680 토큰 이내인가? (초과 시 ATTEMPTS 우선 축소)
```

## 6. 과압축 vs 과잉 전달 균형점

### 과압축의 위험

다음 정보는 제거하면 Advisor의 진단 정확도가 떨어진다:

| 정보 | 왜 제거하면 안 되나 |
|------|------------------|
| 에러 메시지 첫 줄 | Advisor가 에러 유형을 특정하는 핵심 단서 |
| 기각된 가설 목록 | Advisor가 이미 시도된 해결책을 반복 제안하는 것을 방지 |
| HARD_CONSTRAINTS | Advisor가 불가능한 해결책을 제안하는 것을 방지 |
| 시도의 유형 태그 | 접근법의 다양성(다름)을 Advisor가 판단하는 근거 |

### 과잉 전달의 위험

다음 정보는 포함하면 Advisor의 추론이 분산된다:

| 정보 | 대체 표현 |
|------|---------|
| 전체 파일 내용 | `loc: {파일경로:라인}` (Advisor가 필요하면 요청) |
| 전체 스택 트레이스 | `msg:` 에 첫 줄만 |
| 시도의 추론 과정 | `→ {결과 5단어}` 만 |
| 프로젝트 전체 배경 | 생략 (Advisor는 도메인 전문가) |
| 동일 에러 N회 반복 | `×N: [반복]` 콜랩스 |

### 추가 정보가 필요할 때

ACP가 너무 압축됐다고 느껴지면, 먼저 ACP를 전달하고 Advisor가 필요한 추가 정보를 요청하게 한다. 처음부터 모든 것을 전달하는 것보다 Advisor의 질문에 답하는 2회 교환이 더 효율적이다:

```
1회차: ACP 전달 (압축된 핵심 정보)
Advisor 응답: "A3 시도에서 구체적으로 어떤 환경변수명을 사용했나요?"
2회차: 특정 추가 정보만 전달

총 컨텍스트: ACP(~400 토큰) + 추가 정보(~100 토큰) = ~500 토큰
vs 전체 히스토리 전달: ~3000+ 토큰
```
